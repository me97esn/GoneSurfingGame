# Spec: Rail Lift Gating — Roll-Based, Not Heading-Based

## Overview

Replace the heading-based gate on `railLiftForce` in `AFluidDynamics::calcLiftForce` ([FluidDynamics.cpp:528-559](../Source/GoneSurfing/FluidDynamics.cpp#L528-L559)) with a roll-based gate. The current heading-based gate fires the rail that's facing a particular world-Y direction; the physically correct gate fires the rail that's actually submerged in the water.

Targets the "rolling away from wave doesn't yaw away from wave" symptom observed 2026-06-06 on `phone-2026-06-06-21-58-51.csv`: with the right rail dipped, the left rail (raised, out of water) was producing rail lift toward where the right rail sits, partially offsetting the lateralTurn carve direction.

Scope: change the `shouldApplyRailLift` predicate at lines 535-542. No new coefficients. No change to the lift magnitude formula or its direction sign. Existing `RailLiftMagnitude` / `debugLift` UPROPERTYs stay.

This supersedes the "Which Rail Gets Lift?" section of [RailLift_spec.md](../Source/GoneSurfing/RailLift_spec.md). The original spec's heading-direction reasoning ("waves travel in +X, so rail-into-wave-face is determined by board heading") was a simplifying assumption that holds only when the board's roll is locked to its heading.

## Background

Rail lift is Bernoulli suction generated by water flowing past the curved rail. The physical precondition is that the rail is submerged in the water. Only the dipped rail develops the pressure differential; the raised rail is in air (or barely wetted) and produces no useful lift.

The original implementation at [FluidDynamics.cpp:535-542](../Source/GoneSurfing/FluidDynamics.cpp#L535-L542) gates on `forwards.Y`:

```cpp
if (this->side == ESide::VE_Left  && forwards.Y > +0.1f) shouldApplyRailLift = true;
if (this->side == ESide::VE_Right && forwards.Y < -0.1f) shouldApplyRailLift = true;
```

This assumes:
- Waves travel in +X world direction (hardcoded into the comment, not a runtime parameter).
- The board surfs perpendicular to wave direction, i.e., along ±Y.
- The board's roll is correlated with which way along the wave it's heading.

Under those assumptions, the rail facing into the wave face is determined by the sign of `forwards.Y` and is also (loosely) the dipped rail. In practice the assumption fails:

1. **Carving**: when the surfer rolls the board independently of heading direction. Roll changes faster than heading. In a hard carve the dipped rail can be on the opposite side from what the heading gate predicts.
2. **Roll-away maneuver**: when the surfer leans away from the wave, the rail closer to the wave is raised and the rail away from the wave is dipped — but `forwards.Y` may still indicate the heading-determined rail.
3. **Surfing both directions on the wave**: the +X wave-travel assumption breaks down on the second half of any traversal.

### Observed misfire (2026-06-06)

From `phone-2026-06-06-21-58-51.csv` at tick 666 (right rail dipped per the player's input, `waveRollSin = −0.057`):

| state | value |
|---|---|
| `board.forwards` | `(−0.405, +0.914, 0)` |
| `forwards.Y` | `+0.914` (> 0.1 threshold) |
| Gate fires | `VE_Left` (left rail) |
| Right-rail (dipped) firing? | **No** |
| `waveRelativeRollSin` | −0.057 → right-labeled rail submerged |

The raised left rail produced ~150 kN of phantom lift in the wrong direction (toward where the right rail physically sits), partially canceling the lateralTurn force.

### Sign convention for the new gate

Empirically verified on the same trace:

- Bottom actors labeled `bottom_left_*` sit at +Y world initially; `board.left` initially points to world −Y. So **left-labeled actors are on the `−board.left` side** of the board physically.
- Right-labeled actors (`bottom_right_*`, `rail_right_*`) are on the **`+board.left` side**.
- `waveRelativeRollSin > 0` corresponds to the `+board.left` side rising (equivalently `−board.left` side dipping, i.e., **LEFT rail dipped**).
- `waveRelativeRollSin < 0` corresponds to the `−board.left` side rising (i.e., **RIGHT rail dipped**).

So the gate predicate is:

```cpp
if (this->side == ESide::VE_Left  && waveRollSin > +rollThreshold) shouldApplyRailLift = true;
if (this->side == ESide::VE_Right && waveRollSin < -rollThreshold) shouldApplyRailLift = true;
```

The threshold magnitude is small (proposed 0.02, ~1.1°) so even gentle rolls engage the appropriate rail, but the board's slight wave-relative tilt at rest doesn't accidentally fire both rails or jitter between them.

## Implementation

Single-site change in `AFluidDynamics::calcLiftForce` at [FluidDynamics.cpp:528-542](../Source/GoneSurfing/FluidDynamics.cpp#L528-L542). Replace the comment + gate block with:

```cpp
// Determine which rail receives Bernoulli lift based on which rail is physically
// submerged. Uses waveRelativeRollSin (sign indicates which rail is dipped relative
// to the wave surface). Replaces the prior heading-based gate that assumed waves
// travel +X and the board's roll tracks its heading — neither assumption holds
// during carving or roll-away maneuvers. See specs/rail-lift-roll-gate.md.
//
// Sign mapping: waveRollSin > 0 → +board.left side rises → -board.left side dips
//   → LEFT-labeled rail (which sits on -board.left side) is the dipped one → VE_Left fires.
// waveRollSin < 0 → opposite → VE_Right fires.
bool shouldApplyRailLift = false;
const float rollThreshold = 0.02f;
const float waveRollSin = (float)this->sharedCalculations->waveRelativeRollSin;
if (this->side == ESide::VE_Left  && waveRollSin >  rollThreshold) shouldApplyRailLift = true;
if (this->side == ESide::VE_Right && waveRollSin < -rollThreshold) shouldApplyRailLift = true;
```

The lift magnitude calculation (`calcRailLiftForceAmount`) and direction (`±board.left` per side) are unchanged. Only the *which rail engages* predicate changes.

## Acceptance criteria

1. **Right-rail-dipped trace** (`phone-2026-06-06-21-58-51.csv`, post-handoff): `VE_Right` rail actors fire rail lift during the negative-`waveRollSin` segment (ticks ~580-680). `VE_Left` rail actors do not fire during that segment.
2. **Symmetric behavior** on left-rail-dipped traces (e.g. `phone-2026-06-04-20-12-58.csv`): `VE_Left` fires, `VE_Right` does not, during positive-`waveRollSin` segments.
3. **Yaw effect**: on the right-rail-dipped trace, the heading rotates more CW (toward the carve direction) than the pre-fix baseline at tick 760. Quantitative threshold: ≥10° additional CW rotation at tick 760 vs. the baseline run. (Run variance is large; this isn't a snapshot regression test, just a sanity-check the change actually moves the board.)
4. **No regression on lateralTurn**: front-half lateralTurn yaw torque per category at peak roll (within 30% of pre-fix value) — confirms we didn't disturb the lateralTurn force budget.

## Out of scope

- Re-tuning `RailLiftMagnitude` — if the dipped-rail lift turns out too strong or too weak after the gate fix, that's a coefficient adjustment in the editor, not a code change.
- Smoothstep transition through `waveRollSin = 0` (i.e., gradual hand-off between the two rails as roll crosses zero). A simple hard threshold at ±0.02 is sufficient for the symptom; smoothstep can be added if the sudden switch produces visible jitter at near-zero roll.
- The mirror-image debate over rail lift direction sign (the existing commit `92a85fe6d` flipped the sign, which we discussed but parked). Not changing direction sign here.
- Drag-side rail gate ([FluidDynamics.cpp:222-223](../Source/GoneSurfing/FluidDynamics.cpp#L222-L223) uses `cosYawAngleOfAttackLeft` for rail drag engagement, which is a related but different concern).
